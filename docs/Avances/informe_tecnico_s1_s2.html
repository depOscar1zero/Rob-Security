1 — Diagrama de Conexiones

El prototipo está compuesto por un microcontrolador NodeMCU ESP8266 conectado a un sensor PIR HC-SR501 (entrada digital) y un buzzer activo (salida digital). El microcontrolador se comunica vía WiFi con Firebase Realtime Database, que actúa como broker bidireccional entre el hardware y la aplicación Android.

3 — Estructura del Código Fuente

El proyecto cuenta con dos implementaciones de firmware. El firmware base (CodigoArduino/) fue el entregable de S1–S2 y ya funciona con Firebase. El firmware completo (firmware/fitcore_security/fitcore_security.ino) añade la máquina de estados, historial de eventos y control bidireccional. Los fragmentos siguientes provienen del firmware completo por documentar las funcionalidades requeridas.

3.1 Funcionamiento del sensor (lectura PIR)

El HC-SR501 entrega una señal digital que se lee con digitalRead(). No requiere conversión analógica ni debounce, ya que el sensor integra internamente un circuito de disparo y retención.

// ── Pinout ────────────────────────────────────────────────────────
#define PIN_PIR     D2   // HC-SR501 OUT  (3.3 V tolerant, directo)

// ── Variables de estado ───────────────────────────────────────────
bool motionDetected = false;

// ── Setup ─────────────────────────────────────────────────────────
void setup() {
  pinMode(PIN_PIR, INPUT);            // entrada sin pull-up/down
  // El PIR necesita ~30 s de calentamiento antes de dar lecturas estables
  Serial.println("[PIR] Calentando 30 s...");
}

// ── Lectura en el loop ────────────────────────────────────────────
void loop() {
  // Lectura directa: HIGH = movimiento detectado, LOW = zona libre
  motionDetected = (digitalRead(PIN_PIR) == HIGH);

  Serial.printf("[PIR] %s\n",
    motionDetected ? "MOVIMIENTO" : "sin movimiento");

  // El loop se ejecuta cada 100 ms (delay al final del loop)
  delay(100);
}

3.2 Funcionamiento del actuador (control buzzer)

El buzzer activo solo necesita una señal HIGH/LOW. La función setBuzzer() evita escrituras redundantes comparando el estado actual antes de cambiar el pin.

#define PIN_BUZZER  D5   // Buzzer activo 5V

bool buzzerActive = false;

// ── Inicialización ───────────────────────────────────────────────
void setup() {
  pinMode(PIN_BUZZER, OUTPUT);
  digitalWrite(PIN_BUZZER, LOW);     // asegurar que empieza apagado
}

// ── Control del buzzer (sin escrituras redundantes) ──────────────
void setBuzzer(bool on) {
  if (on == buzzerActive) return;   // evitar toggle innecesario
  buzzerActive = on;
  digitalWrite(PIN_BUZZER, on ? HIGH : LOW);
}

// Uso en la máquina de estados:
//   setBuzzer(true)  → activa alarma sonora
//   setBuzzer(false) → silencia la alarma

3.3 Módulo de conexión WiFi

La conexión WiFi se realiza en modo Station (STA). El loop principal incluye una rutina de reconexión automática no bloqueante para recuperarse de desconexiones sin reiniciar el dispositivo.

#include <ESP8266WiFi.h>
#include "secrets.h"   // WIFI_SSID y WIFI_PASS (no en el repo)

// ── Conexión inicial ─────────────────────────────────────────────
void connectWiFi() {
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("[WiFi] Conectando");
  while (WiFi.status() != WL_CONNECTED) {
    delay(400);
    Serial.print(".");
  }
  Serial.printf("\n[WiFi] OK · IP: %s\n",
    WiFi.localIP().toString().c_str());
}

// ── Reconexión automática en el loop ─────────────────────────────
void loop() {
  if (WiFi.status() != WL_CONNECTED) {
    Serial.println("[WiFi] Reconectando...");
    WiFi.reconnect();
    delay(1000);
    return;   // omitir resto del loop hasta reconectar
  }
  // ... resto de la lógica
}

La comunicación con Firebase se realiza mediante peticiones HTTPS REST sobre WiFiClientSecure. Las credenciales se separan en secrets.h, que está excluido del repositorio por .gitignore.

3.5 Métodos para escritura y lectura en la base de datos

Se implementaron tres métodos HTTP sobre Firebase REST API, todos no bloqueantes al nivel del sketch principal (se invocan en intervalos con millis() en lugar de delay()):

FunciónMétodo HTTPUso
fbPUT(path, body)PUTSobreescribir un nodo completo (p.ej. /sensor)
fbGET(path)GETLeer un nodo (p.ej. /config/armado)
fbPOST(path, body)POSTAgregar elemento con pushId único (historial /alertas)
 
// ── ESCRITURA: PUT sobreescribe el nodo completo ─────────────────
bool fbPUT(const String& path, const String& body) {
  HTTPClient http;
  String url = "https://" FIREBASE_HOST + path + ".json?auth=" FIREBASE_API_KEY;
  if (!http.begin(tlsClient, url)) return false;
  http.addHeader("Content-Type", "application/json");
  int code = http.PUT(body);
  http.end();
  return (code == 200);
}

// ── LECTURA: GET retorna el JSON del nodo ────────────────────────
String fbGET(const String& path) {
  HTTPClient http;
  String url = "https://" FIREBASE_HOST + path + ".json?auth=" FIREBASE_API_KEY;
  if (!http.begin(tlsClient, url)) return "null";
  int    code = http.GET();
  String resp = (code == 200) ? http.getString() : "null";
  http.end();
  return resp;
}

// ── POST: agrega elemento nuevo con pushId único (historial) ─────
bool fbPOST(const String& path, const String& body) {
  HTTPClient http;
  String url = "https://" FIREBASE_HOST + path + ".json?auth=" FIREBASE_API_KEY;
  if (!http.begin(tlsClient, url)) return false;
  http.addHeader("Content-Type", "application/json");
  int code = http.POST(body);
  http.end();
  return (code == 200);
}
// ── Publicar estado del sensor (escritura periódica cada 1 s) ────
void postSensorData() {
  JsonDocument doc;
  doc["movimiento"]  = motionDetected;
  doc["estado"]      = stateLabel[static_cast<uint8_t>(state)];
  doc["alerta"]      = (state == State::ALERT || state == State::ALARM);
  doc["timestamp"]   = millis();

  String body;
  serializeJson(doc, body);
  fbPUT("/sensor", body);   // PUT sobreescribe /sensor completo
}

// ── Leer configuración remota (lectura cada 2 s) ──────────────────
void syncConfig() {
  String resp = fbGET("/config");
  if (resp == "null") return;

  JsonDocument doc;
  if (deserializeJson(doc, resp) != DeserializationError::Ok) return;

  bool armado = doc["armado"].as<bool>();
  if (!armado && state != State::DISARMED && state != State::WARMUP) {
    state = State::DISARMED;          // app desarmó el sistema
    setBuzzer(false);
  } else if (armado && state == State::DISARMED) {
    state = State::ARMED;             // app armó el sistema
  }
}

// ── Timers en el loop (no bloqueante con millis) ──────────────────
unsigned long tPost = 0, tRead = 0;

void loop() {
  unsigned long now = millis();

  if (now - tPost >= 1000UL) {   // publicar estado cada 1 s
    tPost = now;
    postSensorData();
  }
  if (now - tRead >= 2000UL) {   // leer comandos cada 2 s
    tRead = now;
    syncConfig();
  }
}

3.6 Códigos adicionales implementados

a) Máquina de estados finita (FSM)

En lugar de un simple if/else, el firmware modela el comportamiento del sensor como una máquina de estados con cinco estados bien definidos, lo que previene falsos positivos y permite una alarma sostenida.

enum class State : uint8_t {
  WARMUP, DISARMED, ARMED, ALERT, ALARM
};
const char* stateLabel[] = {
  "calentando", "desarmado", "armado", "alerta", "alarma"
};

State        state    = State::WARMUP;
unsigned long alertTs = 0;
unsigned long clearTs = 0;

void updateFSM(unsigned long now) {
  switch (state) {

    case State::WARMUP:
      if (now - tBoot >= 30000UL) {
        state = State::ARMED;          // listo tras 30 s de calentamiento
      }
      break;

    case State::ARMED:
      if (motionDetected) {
        state   = State::ALERT;
        alertTs = now;
        pushEvent("alerta");           // registrar en /alertas
      }
      break;

    case State::ALERT:
      if (!motionDetected) {
        state = State::ARMED;           // movimiento breve, volver a armado
      } else if (now - alertTs >= 3000UL) {
        state = State::ALARM;           // 3 s sostenido → alarma
        pushEvent("alarma");
      }
      break;

    case State::ALARM:
      setBuzzer(true);
      if (!motionDetected) {
        if (clearTs == 0) clearTs = now;
        else if (now - clearTs >= 5000UL) {  // 5 s sin movimiento
          state = State::ARMED;
          clearTs = 0;
          setBuzzer(false);
          pushEvent("despejado");
        }
      } else { clearTs = 0; }         // reiniciar si vuelve a detectar
      break;

    case State::DISARMED:
      setBuzzer(false);
      break;
  }
}

b) Registro de historial de eventos

Cada transición relevante (alerta, alarma, despejado) genera un POST a /alertas. Firebase asigna automáticamente un pushId único, lo que permite un historial ordenado cronológicamente sin colisiones.

void pushEvent(const char* tipo) {
  JsonDocument doc;
  doc["tipo"]      = tipo;
  doc["timestamp"] = millis();

  String body;
  serializeJson(doc, body);
  fbPOST("/alertas", body);  // POST genera -NxPushId único automáticamente
  Serial.printf("[Event] %s → /alertas\n", tipo);
}

c) App Android — lectura en tiempo real (React Native / Expo)

La app usa el SDK de Firebase Web v9 con onValue(), que mantiene una conexión WebSocket persistente y entrega actualizaciones en tiempo real sin polling. El estado se muestra con tarjetas de color condicionadas al valor del sensor.

// app/src/firebaseConfig.js — inicialización con variables de entorno
import { initializeApp, getApps } from 'firebase/app';
import { getDatabase } from 'firebase/database';

const firebaseConfig = {
  apiKey:            process.env.EXPO_PUBLIC_FIREBASE_API_KEY,
  authDomain:        process.env.EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN,
  databaseURL:       process.env.EXPO_PUBLIC_FIREBASE_DATABASE_URL,
  projectId:         process.env.EXPO_PUBLIC_FIREBASE_PROJECT_ID,
};

// Evitar re-inicialización en hot reload de Expo
const app = getApps().length === 0
  ? initializeApp(firebaseConfig)
  : getApps()[0];

export const db = getDatabase(app);
// app/App.js — suscripción en tiempo real y UI reactiva
import { ref, onValue } from 'firebase/database';
import { db } from './src/firebaseConfig';

const SENSOR_PATH = '/sensor/movimiento';

export default function App() {
  const [motion, setMotion] = useState(null);
  const [connected, setConnected] = useState(false);

  useEffect(() => {
    const sensorRef = ref(db, SENSOR_PATH);
    const unsub = onValue(sensorRef,
      snapshot => { setMotion(snapshot.val()); setConnected(true); },
      error   => { setConnected(false); }
    );
    return () => unsub();  // cleanup al desmontar
  }, []);

  const detected = Boolean(motion);
  return (
    <View style={[styles.card, detected ? styles.cardAlert : styles.cardClear]}>
      <Text>{detected ? '🚨 MOVIMIENTO DETECTADO' : '✅ SIN MOVIMIENTO'}</Text>
    </View>
  );
}

4.1 Estructura del schema RTDB

La base de datos sigue una estructura plana con tres nodos raíz: /sensor (estado en tiempo real escrito por el firmware), /config (comandos de control escritos por la app), y /alertas (historial inmutable generado por POST). Esta separación de responsabilidades evita condiciones de carrera y facilita la aplicación de reglas de seguridad por nodo.

5 — Evidencia de Funcionamiento Bidireccional

5.1 Flujo 1 — Sensor físico → Firebase (unidireccional base)

  1. El PIR detecta movimiento (señal HIGH en D2).
  2. La FSM transiciona de ARMED → ALERT y, si el movimiento se sostiene 3 s, a ALARM.
  3. El firmware serializa { movimiento: true, estado: "alarma", alerta: true, timestamp: ... } y ejecuta fbPUT("/sensor", body).
  4. Simultáneamente, pushEvent("alarma") ejecuta fbPOST("/alertas", body).
  5. Firebase RTDB actualiza el nodo /sensor y crea un nuevo registro bajo /alertas/{pushId}.
  6. La app Android recibe la actualización por WebSocket (latencia esperada < 500 ms en LAN).
  7. La tarjeta de la app cambia a rojo y muestra "MOVIMIENTO DETECTADO".

5.2 Flujo 2 — Firebase → actuador físico (control remoto bidireccional)

  1. El operador (o la app) escribe false en /config/armado en la consola de Firebase.
  2. El firmware lee /config/armado cada 2 s mediante fbGET("/config").
  3. Al detectar armado: false, la FSM transiciona al estado DISARMED.
  4. setBuzzer(false) apaga inmediatamente el buzzer.
  5. El siguiente ciclo de escritura publica estado: "desarmado" en /sensor.
  6. La app refleja el nuevo estado con gris (sistema desarmado).
  7. Al escribir armado: true, el sistema vuelve a ARMED y monitorea nuevamente.
✅ Flujo bidireccional confirmado El canal de escritura (ESP8266 → Firebase → App) y el canal de control (App → Firebase → ESP8266) operan de forma independiente y en tiempo real. La latencia total ESP8266 → Firebase → App es tipicamente < 1 s en red local con buena señal WiFi.
